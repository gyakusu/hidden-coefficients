## 2. 【P1】配属シャッフル：構造のシード乱数化

### 2.1 コンセプト——「どの部署に配属されるかは選べない」

ゲーム開始時にプレイヤーは **架空の部署に配属** される（例：調達部・営業部・企画部・開発部…）。部署はフレーバーテキストを与えるが、**本当の意味は「隠れた係数構造の割り当て（＝シード）」** である。

- どの項目が「ゲート付き主力」か、どれが「成果ゼロの信頼源」かが、配属ごとに変わる。
- 現実対応もきれいに繋がる：調達部ならVA提案が主戦場だが、企画部なら会議（意思決定の場）こそが主戦場かもしれない。**「前の部署の成功体験が次の部署で通用しない」は、このゲームの主題そのもの**（「昨年の結論は今年の保証ではない」の部署間版）。
- 原作の一節「定数だった社員一人一人の意識が、大きな変数となった」に足す命題：**「あなたが学んだのは『答え』だったのか、『答えの見つけ方』だったのか——配属が変われば分かる。」**

### 2.2 何を乱数化し、何を固定するか

無制約に乱数化すると推定不能になる（設計改訂2026-07 §4 の教訓）。**「形の語彙」は固定し、「形と項目の対応」と「パラメータ」だけを振る**：

| 層 | 扱い | 内容 |
|----|------|------|
| **応答形状の語彙** | **固定** | ゼロ・弱線形（ダミー）・年内凹・累積凹・ゲート付き線形・遅延線形の6種。全部署でこの6種が必ず1つずつ存在する（罠の対称性テーブルは全配属で成立） |
| **形状⇄項目の対応** | **シードで置換** | ただし全単射置換ではなく**もっともらしさ制約付き**（§2.3）。会議が「ゲート付き主力」になる部署もある（企画部） |
| **パラメータ** | **シードでジッタ** | 係数・TAU・ゲート閾値を設計値の±25〜30%で振る。序列（主力≫中堅≫ダミー）は不変条件として保証 |
| **信頼の三役・市況・ノイズ構造** | **固定** | ゲームの心臓部。ここが変わると「別のゲーム」になる |

### 2.3 もっともらしさ制約（ナラティブ整合）

完全ランダム置換は「報告が真の主力」のような、種明かし時に納得感のない配役を生む。項目を**性質クラス**に分け、クラス内でのみ置換する：

- **主力候補クラス**（ゲート付き線形 or 累積凹が入りうる）：VA提案・現場訪問・会議・資料作成
- **信頼源クラス**（成果ゼロ or 遅延が入りうる）：報告・育成・現場訪問
- 現場訪問は両クラスに属する蝶番（どちらに転ぶかも配属次第）——現行構造はこの生成規則の1標本にすぎなくなる。

種明かしでは「この部署では会議が意思決定の主戦場だった。あなたの前の部署の常識は、ここでは通用しなかった」のように、**配役の理由を部署フレーバーで説明**する。

### 2.4 シードの運用——フリープレイと研修モード

| モード | シード | 用途 |
|--------|--------|------|
| フリープレイ | ランダム配属（シードは結果画面に表示） | リプレイ。「もう一度同じ部署」も選べる |
| **合言葉モード** | 任意の文字列（例：`2026年新人研修A班`）をハッシュしてシード化 | **研修の同期**。同じ合言葉なら全員同じ部署・同じ市況系列 → デブリーフで比較可能。翌期は合言葉を変えるだけで「答えの伝承」が無効化される |

### 2.5 実装スケッチ

エンジンは既にRNG注入可能な純粋関数なので、変更は「configの定数を、シードから生成される構造体に置き換える」ことに集約される：

```
src/game/scenario.ts（新規）
  generateScenario(seed) → { roleAssignment, coefs, taus, gates, deptFlavor }
config.ts   → 生成の基準値と揺らし幅（SCENARIO_JITTER 等）の置き場に再編
engine.ts   → COEF 直参照を scenario 経由に変更（ロジック自体は不変）
hints.ts    → 項目名の直書きを roleAssignment 経由に変更
TitleScreen → 配属演出（部署名・辞令）／合言葉入力欄
engine.test.ts → キャリブレーションを「N個のシードでプロパティテスト化」
                （全シードで 上級>均等>罠、全シードで6形状が全て存在、等の不変条件を検証）
```

**キャリブレーションのプロパティテスト化が本丸**。単一構造の手調整バランスを、生成規則のバランス保証に格上げする。ここが一番工数がかかり、一番価値がある。

### 2.6 設計原則（改訂2026-07 §2.2）との整合チェック

1. 「効き方の形を事前開示しない」→ **強化される**（部署名は雰囲気しか語らない。むしろ思い込みを誘うダミーシグナルとして機能）
2. 「メカニクスの追加を項目の追加で行わない」→ **遵守**（項目は6つのまま。増えたのは構造の生成規則）
3. 「形の発見は配分を変える実験でのみ」→ **不変**
4. 「昨年の結論は今年の保証ではない」→ **拡張**（プレイ間にも適用：「前回の結論は今回の保証ではない」）

## 3. 【P2】初見体験の救済——沼と理不尽の境界管理

### 3.1 方針

沼は削らない。追加するのは **「進んでいる感覚」** であって「答え」ではない。構造のヒントを増やすのではなく、(a) 序盤に1つだけ確実な足場を与え、(b) プロセスの手応えを常時可視化し、(c) 中間に1回だけ「問いに答えてもらえる」機会を置く。

### 3.2 (a) OJTメンター（1〜3年目限定の確定シグナル）

現行設計では「信頼が低い年のヒントは曖昧orミスリード」。これは首尾一貫しているが、**初見の1年目＝信頼最低＝ヒント最低品質＝罠に一番ハマりやすい年**、という残酷な重なりを生んでいる。

- 1〜3年目のみ登場するNPC「メンターの先輩」が、毎年 **1つだけ嘘のない発言** をする。
- 発言は**構造の開示ではなくプロセスの指導**に限定：「1年のデータで決めつけるのはやめておけ」「同じ配分を繰り返しても、ブレが均せるだけで形は見えないぞ」「効かなかった項目、本当に*効かない*のか？ *まだ*効かないのか？」
- 3年目で異動していなくなる（=確定情報の供給が絶たれ、本番の沼が始まる）。**チュートリアルを別モードにせず、世界の中に置く。**

### 3.3 (b) プロセス指標の常時表示と初年度の成功体験

- 既存の年度末レビューのプロセス指標（探索度・投資率）を、**結果の数字より先に**表示する順序に変える。低スコアの年でも「今年は良い実験をした」が先に目に入る。
- 資料作成の凹性（150hで63%）を序盤の成功体験として活用する：1年目に資料へ少しでも振っていれば成果に見える形で寄与するので、結果画面の定性文で「早い段階で手応えのあった項目が少なくとも1つある」ことを（項目名は伏せて）保証する。**「何も分からなかった」ではなく「何かは効いた。どれかは分からない」で1年目を終えさせる。**

### 3.4 (c) 昇進面談：仮説を1つだけ検証できる

5年目の昇進イベントを、演出から**意思決定**に格上げする：

> 新しい上司との面談。これまでの仮説ノートから **1つを選んで検証してもらえる**（正しい／間違い、の二値のみ。係数値は言わない）。

- どの仮説を検証に使うかはプレイヤーの選択＝**情報も配分対象である**というゲームの主題をメカニクスで反復。
- 信頼が閾値未満なら上司の答えは「さあな、自分で確かめろ」（検証権が得られない）——信頼の三役に**四役目（検証権）**が加わり、序盤の信頼投資の動機がまた一つ増える。
- 沼の保全：開示は二値1bitのみ・ゲーム中1回のみ・エンディングの種明かしのカタルシスは温存される。

### 3.5 (d) 初見エピローグ

初回プレイ（localStorage判定）のエンディングでは、ランク表示の前に仮説の変遷（何年目に何に気づいたか）を先に見せ、「初見のS評価は想定されていない。このゲームの初回の成果は点数ではなく、あなたの推定の履歴だ」という一文を添える。低ランク＝失敗体験、の回路を最初の1回だけ明示的に切断する。

## 4. 【P3】研修キット——ゲームの外側を設計する

### 4.1 成果物一覧

| 成果物 | 形式 | 内容 |
|--------|------|------|
| ファシリテーターガイド | `docs/workshop-guide.md` | 進行台本（90分想定：プレイ50分＋デブリーフ40分）、年次の介入ポイント（3・6年目に手を止めて班討議）、**誤読対策スクリプト**（下記4.2） |
| 合言葉シード | §2.4 の研修モード | 全員同一構造・同一市況でプレイ→個人差＝意思決定の差、として比較可能に |
| プレイログのエクスポート | 結果画面からJSON/URLコピー | 各人の配分履歴・仮説変遷をデブリーフで並べる素材。「同じ部署・同じ市況で、なぜ差がついたか」 |
| 転移ワークシート | ガイドに同梱 | 「あなたの実務で『ゲートが閉じているだけ』の項目は何か」「あなたが会議最低200回だと思っている制約はどれか。それは上申で外せないのか」 |

### 4.2 誤読対策（デブリーフで必ず扱う）

| 予想される誤読 | 対応スクリプト |
|--------------|--------------|
| 「報告は成果ゼロ＝社内政治をやれというゲームだ」という冷笑 | 信頼は政治力ではなく**観測インフラ**である（信頼が低いと成果が出ないだけでなく、何が効いているか*見えなくなった*ことをプレイログの実データで示す） |
| 「正解はVA提案」という項目の暗記（which の学習） | 合言葉を変えた2周目を予告する。「次の部署でもVAに全振りするか？」——学ぶべきは *which* ではなく *how*（配属シャッフルが前提装備である理由） |
| 「運が悪かっただけ」への逃避／「高得点＝自分の実力」への慢心 | 素点と実力点の乖離データをそのまま見せる（既存機能）。両方向の乖離者を1人ずつ指名して感想を聞く |

### 4.3 依存関係

4.1 のうちガイドとワークシートは**今すぐ書ける**（実装不要）。ただし合言葉シードなしで運用すると翌期に教材価値が減衰するため、**研修キットの正式リリースは P1 とセット**にする。ログエクスポートは小規模なUI追加のみ。

## 6. バランス上のリスクと対策

| リスク | 対策 |
|--------|------|
| 乱数化した構造の中に「詰み配属」（9年で同定不能・または自明すぎ）が混入する | キャリブレーションのプロパティテスト（§2.5）で全シード不変条件を担保。加えて生成規則側で制約（主力の初期ゲート閾値に上限、ダミーと主力の係数比に下限）。CIで数百シードを回す |
| 部署フレーバーが逆に構造のシグナルになる（「調達部＝VAが主力」と学習される） | 部署名と構造の対応もシャッフルに含める（同じ部署名でも中身が違いうる）。フレーバーは「もっともらしい思い込み」を誘うダミーとして明示的に設計する |
| メンター（§3.2）が攻略手順の配布装置になる | 発言をプロセス指導に限定し、項目名を一切口にしない語彙で書く。発言プールをレビューし「構造を1bitでも開示していないか」を基準に検閲 |
| 昇進面談の検証（§3.4）が強すぎて中盤の沼が消える | 二値1bit・1回限り・信頼ゲート付き。効きすぎる場合は「上司も間違うことがある（信頼度に応じた正答率）」をチューニング弁として留保 |
| 乱数化で「作者の手調整による味」が薄まる | 現行構造を「調達部」としてシード空間内に**必ず含める**（レギュラー配属）。手調整の味は保存され、乱数化はその周りに空間を張る |
